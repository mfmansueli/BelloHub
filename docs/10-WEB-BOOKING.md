# 10 · The client web app (booking, management, portal, sealed forms)

The professional's clients use **no app**. They open links on any device: usually from a WhatsApp message, often inside **WhatsApp's or Instagram's in-app browser**, often on a mid-range or old Android phone, sometimes on a laptop. This web app is half the product's first impression. It lives in `web/` in the same repository (D27).

Screens are in the prototype as `Bk-1…Bk-11` (booking) and `Cl-1…Cl-9` (client). `Cl-1-Reminder` and `Cl-8-Reminder` are **pictures of the WhatsApp messages** the client receives (message templates, `07-LOCALIZATION.md` §6), not web pages; their web destinations are the pages they link to.

## 1. Stack and structure

- **TypeScript + Vite + Preact** (no router library: a ~1 KB History API router), plain CSS with custom properties generated from the design tokens, **no UI framework, no CSS-in-JS, no third-party scripts, no analytics, no cookies**.
- Self-hosted subsets of Fraunces and DM Sans (Latin and Latin Extended, so Portuguese, Spanish, Italian, French, German, Turkish and Indonesian render correctly), `font-display: swap`, preload the two used weights. Arabic and Devanagari use system font stacks (no downloads). Fallback stacks sized to avoid layout shift.
- i18n: own tiny module, JSON per localization (`web/src/i18n/{pt-BR,pt-PT,es-MX,es-419,es,en,en-GB,it,fr,de,tr,id,hi,ar}.json`; `es-419` and `en-GB` generated by `derive-locales.py`), same keys as the iOS catalog where the string is shared; `Intl` for dates, times, money, plurals (six forms in Arabic), lists. Right-to-left, logical CSS, bidi isolation and digit normalization as in `07-LOCALIZATION.md` §7. Each language's JSON is loaded on demand (≤ 15 KB gzip each) so the initial bundle budget holds.
- Crypto: `hpke-js` (`@hpke/core`, `@hpke/dhkem-x25519`, `@hpke/chacha20poly1305`), pinned, bundled, loaded **lazily only on form/check-in pages**.
- **No Firebase SDK in the browser (D46):** the page keeps `connect-src 'self'` and calls our Cloud Functions over HTTPS on its own origin (`/api/<name>`, `11-BACKEND-FIREBASE.md`); no Auth phone flow, no reCAPTCHA, no third-party script.
- Budgets: initial JS ≤ **80 KB gzip** (crypto chunk loaded later, ≤ 60 KB more), CSS ≤ 15 KB, LCP ≤ 2.5 s on a throttled "Slow 4G, 4× CPU" profile, no layout shift > 0.05.
- Folder: `web/src/{app,routes,components,i18n,crypto,api,styles,lib}`, `web/test/{unit,e2e,vectors}`, `web/public/.well-known/`.

## 3. The booking flow

State machine `service → time → you → verify → [questions] → (confirmed | review)`; the bar at the top shows progress, back works everywhere, and the chosen values persist in `sessionStorage` (non-clinical only) so a refresh does not lose them.

- **Availability**: `GET getSlots?slug&serviceId&addOns&guests&from&to` returns free start times for the **total duration** (service + add-ons + guests in sequence) computed server-side from `availability` (rules, breaks, days off, blocks, existing bookings, buffer, **minimum notice** and **max horizon** settings, and the professional's time zone). Show times in the **business time zone**, label it ("15:00 in São Paulo"), and warn when the device zone differs. The times follow D56: the slot grid she chose plus starts anchored right after and right before her visits, breaks and blocks (a 75-minute service after a visit that ends at 10:05 with a 10-minute buffer is offered at 10:15), and the extra time and processing time of each service. With "Keep my day compact" on (the default) `slots` holds the times that leave no unbookable gap and `more` the other free times: the page shows `slots` and a quiet **"Show all times"** link that reveals `more` in place (the link is absent when `more` is empty). Every time in either list can be held and booked.
- **Hold**: choosing a slot calls `holdSlot` (5-minute soft hold, cleaned automatically) so two people do not collide while typing. Sending a booking code with the browser's `holdKey` stretches a live soft hold to the code's 10 minutes (API.md 5.5), so waiting for the e-mail does not lose the time.
- **Verification** (D31, **D46: e-mail only**, D57): an e-mailed 6-digit code (Functions `sendEmailCode`/`verifyEmailCode`, hashed, 30-minute expiry, 5 attempts, resend after 30 s). There is no SMS and no phone verification on the page (no Firebase SDK, strict CSP); the prototype's SMS/WhatsApp chooser is not built. "Resend in 0:24" countdown. Codes are never logged. The client can **correct the address** right on Bk-6 (the code goes to the new one).
- **"I didn't get the code"** (owner-approved, 2026-10-10): a quiet link after the first wait (or after a resend) opens a sheet: check the spam folder (and the address shown), send a new code, change the address, and, **only when the professional has a public WhatsApp number**, "Confirm with <Name> on WhatsApp". That last one creates the booking as an **unverified request** (`verification: { method: "whatsapp" }`, API.md 5.8): always `pendingApproval`, flagged "Not verified" in her app with a 5-character reference; the review page shows the reference and a button that opens `wa.me/<her number>` with a prefilled message in the page language (first name, service, date, time, reference). Only what was already collected travels (no first-visit note). The time stays held for the request for 24 hours (or until the visit starts) and is released by the cleanup job if she does not answer; no e-mail goes out until she approves (then the confirmation with the personal link). Limits: 5/day per IP, 3/day per e-mail and per phone, at most 2 waiting per contact.
- **Returning clients skip the code**: a booking confirmed with an e-mail code returns a **trusted-device token** (this page, this e-mail, 90 days, hashed on the server, 5 per e-mail and page) that the page keeps in `localStorage` (`bh.device.<slug>`, guarded: an in-app browser that blocks storage just asks for the code). The next booking with the same address on the same page goes from Bk-5 straight to Bk-7; the server refuses the token (`VERIFICATION_REQUIRED`) whenever the booking would wait for her (approval, free registrations, no-show limit) and the page goes back to the code. "Forget this device" on the management page revokes it (`forgetDevice`).
- **Create**: `createBooking` (Function, transaction, D32). Possible results: `confirmed`, `pendingApproval` (new client with approval on, or no-show limit reached) → `Bk-10-Review`, `slotTaken` → back to time with the message "That time was just taken. Here are the next ones", `paused` → `Bk-1` notice. The response contains the **manage token** once; the page also stores it in nothing (the URL is the key).
- **Confirmation** (`Bk-8`): service, add-ons, guests, final time, **the personal link** (copy button), "Add to calendar" (ICS download + Google Calendar link), "Complete your health form" card (first visit only, or after 12 months), "Need to change plans? Use your link." Copy shown depends on channel capability (D31): with automation off it says "Save your link" and, if an email was given, "We emailed it to you"; with automation on it says "A confirmation is on its way to your WhatsApp." The optional "Get Bello Hub" line stays as a quiet, optional note for professionals only (not for clients); **omit it for clients in v1** (the prototype's line addresses curious clients; legal and brand review first).
- **Waitlist**: when no slots, "Join the waitlist" collects name, phone, day range; the professional is told (generic push), and when a slot frees she offers it (opens WhatsApp with a ready message and a one-time hold link). Waitlist items are operational data.
- **Return visits**: the confirmation and portal reuse the same page; the phone is the identity, nothing else (the trusted device above only spares the code; it never identifies anyone).

## 4. The management page (`Bk-9`) and its flows

Shows: service, add-ons, guests, time (business zone), professional, status chip, the professional's **rules** (generated text), and actions depending on state and rules. **Right under the booking card it says "Change or cancel"** (owner, 2026-10-11: the personal link also arrives in her WhatsApp messages, `mintManageLink`, so the page opens on what it is for): Reschedule and Cancel with the policy note; Add to calendar sits in its own card further down. **Where she works** (`PlaceCard`: the address lines, the "how to find us" note, "Open in Apple Maps" / "Open in Google Maps") shows when the server sends it: a confirmed booking, or any booking when she made the address public (the confirmation page shows it too, and the booking page when public). A Playwright test opens the page with WhatsApp's and Instagram's in-app user agents and storage blocked (real in-app browsers stay H8):

- **Confirm I'm coming** (when the policy asks for confirmation): sets `clientConfirmedAt`.
- **Running late**: 10/15/20/30 min buttons → notification to the professional; shows what she replied if she did.
- **Reschedule** (`Cl-9`): per policy and count: *direct* (picks a new slot, immediate), *request* (after the free window: sends `rescheduleRequests`, the old slot stays reserved until she answers), *message* (opens WhatsApp to her). Past `maxReschedules` shows the message path.
- **Cancel** (`Cl-6`): inside the free window → immediate with the honest line "No cost to you" style copy per locale; after the window → either allowed **with an honest warning** (D12) or "message her" per policy. Reason optional. Frees the slot and triggers the waitlist.
- **Add to calendar**, **Message <Name>** (`wa.me`), **Rules**, **Complete health form** (if pending), **My data**.
- States: upcoming, in progress window, past (shows "How did it go?" → check-in link if applicable), cancelled, expired token.

## 5. Sealed forms (the privacy-critical pages)

`Cl-4-Intake` and `Cl-5-CheckIn` and `Cl-7-MyData` follow `06-PRIVACY-SECURITY.md` §3 exactly.

- Load: `getFormContext(token)` returns the form template version (questions, localized labels, required flags, branching for minors), the professional's `inboxKey`, and whether an intake was already completed within 12 months (server flag, no content). No consent text: consents are the professional's own business; the app only records their status (D55).
- Answers live in component state only. **No `localStorage`, `sessionStorage`, cookies, URL, console, analytics or error-reporting payload may contain an answer.** The error boundary logs only an error code.
- Autofill and spellcheck are **off** on clinical fields (`autocomplete="off"`, `spellcheck="false"`, `autocapitalize="off"`) so browsers do not send text to third parties.
- No consent, agreement or signature step of any kind (D55): the page shows nothing to read and agree to, collects no typed or drawn signature, and the only legal link on the booking pages is Bello Hub's own privacy policy.
- Minors: the switch "Is this visit for someone under 18?" reveals the young person's name and the minor questions; no guardian text and no guardian signature.
- Photo for check-in: `<input type="file" accept="image/*">` (camera or library), re-encoded in a canvas to JPEG ≤ 1.5 MB, which also **strips EXIF**; preview with remove.
- Seal and submit, show the exact success copy (`06` §3.5). Network failure: keep the sealed envelope in memory and offer retry (never store).

## 6. Accessibility, performance, security details

- Semantic HTML: real `<button>`, `<a>`, `<label>`, `<fieldset>`/`<legend>`, `<main>`, headings in order; `lang` per page; focus ring 3 px `roseText`; 44 px targets; contrast per `08`; `aria-live="polite"` for errors and countdowns; keyboard-complete flows; forms never trap focus. Lighthouse accessibility ≥ 95, axe-core clean in Playwright.
- Support text zoom to 200 % and 320 px width without horizontal scroll.
- Use `100dvh`/`svh` (not `100vh`) because in-app browsers resize; test with the on-screen keyboard.
- Headers on Hosting (see `06` §6 for CSP): HSTS, CSP, `X-Content-Type-Options`, `Permissions-Policy: ()`, `Referrer-Policy`, `Cross-Origin-Opener-Policy: same-origin`, long immutable caching for hashed assets, `no-store` for `index.html` of token routes.
- Never render professional-supplied text as HTML (no `dangerouslySetInnerHTML`); the public bio and service names are plain text with line breaks only.

## 7. Visual language and motion on the web

Same tokens as the app (generated into CSS variables by a script that reads the DS token file; keep one source). Mobile first, single centered column (max 560 px) on large screens, soft shadows, hero blocks. Motion (inside `@media (prefers-reduced-motion: no-preference)`): `--ease: cubic-bezier(.22,1,.36,1)`, `--soft: cubic-bezier(.3,1.25,.5,1)`; screen blocks rise 14 px and fade with 40 ms stagger (first nine), press scale .97, sheet slide-up .46 s with 3 px-blur scrim, success seal (pop, check draw, one ring), switch knob transition. A page transition is a crossfade of the route container (0.2 s). Use the exact numbers in `09-MOTION.md`.

## 9. Client reminders prepared in the app (D31)

Every link in a message she sends is the full `https://` address on its own line (`ClientLinkText`). A message about
a visit booked through the page carries the client's own link to change or cancel (`mintManageLink`, API.md 6.3);
a visit she added by hand, a cancelled or past one, or a failed call carries her booking page, and the sheet says
which. The calendar file (browser and `getIcs`) has her address as `LOCATION` and its map link in the description when
the booking may see it, and her booking page as the link (D50).


Because v1 does not send WhatsApp automatically, the iPhone prepares reminders:
- At the configured time (default **18:00 the day before**, setting in `NotificationSettings`) the app posts a **generic** local notification ("3 reminders are ready to send").
- `Notifications` and `Home` show a **"Reminders ready"** section (a small design addition built from existing components: a `ListCard` of clients, each row with the time, service, and a "Send" action). Tapping opens WhatsApp with the `reminder` template filled (or `reminderConfirmRequest` when the policy asks for confirmation); the row then shows "Opened" and `reminderSentAt` is set when the app returns to the foreground.
- "Remind again" on `Appointment` (3.2) uses the same path. Clients without a phone or who stopped reminders are skipped.
- If `whatsAppAutomation` is on, the server sends the reminder template and this section hides.

## 10. What the client page must never do

Never show health information, other clients, the professional's habits notes or private notes; never reveal whether a phone number is already a client (use the same response); never use the client's data for anything beyond the booking; never track.
